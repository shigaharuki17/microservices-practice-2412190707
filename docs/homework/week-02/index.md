# 项目选题说明

## 一、项目名称

基于微服务架构的社区报修与上门维修服务平台。

## 二、要解决的实际问题和业务背景

在社区日常管理中，住户经常遇到水管漏水、电路故障、门锁损坏等问题，公共区域也存在照明、设施等维修需求。传统报修主要依赖电话、微信群或纸质登记，容易出现报修信息不完整、重复登记、派单不及时和维修进度难以追踪等问题。同时，维修记录与材料费用分散，物业难以统计维修效率，住户也难以了解收费依据。

本项目计划提供统一的线上报修平台，将住户、物业管理员和维修人员连接起来，形成“提交报修—审核派单—预约上门—维修处理—费用结算—验收评价”的业务闭环。通过集中保存工单、维修记录和费用明细，提高沟通效率，使维修过程可查询、可追踪。

## 三、主要目标用户及其需求

| 目标用户 | 主要需求 |
|---|---|
| 社区住户 | 提交故障描述和图片，预约上门时间，查看处理进度，确认维修报价，完成支付及验收评价。 |
| 维修人员 | 查看分配的工单和故障信息，确认上门时间，更新维修状态，记录维修过程及材料用量。 |
| 物业管理员 | 审核报修并派单，协调人员与预约时间，处理超时工单、返修及投诉，统计维修工作量。 |
| 平台管理员 | 管理用户账号和角色权限，维护维修类别及收费标准，查看平台运行情况。 |

## 四、选择该题目的原因

1. **业务背景明确。** 社区报修贴近日常生活，问题和处理流程容易理解，便于梳理需求与验证功能。
2. **用户角色丰富。** 住户、维修人员和管理员承担不同职责，适合实践身份认证、角色权限以及数据访问控制。
3. **业务流程完整。** 项目包含报修、派单、预约、维修、材料使用、结算和评价，能够支撑数据库设计与业务状态管理。
4. **具有合理的服务拆分空间。** 用户、工单、调度、材料和结算等模块职责相对清晰，可以随着课程进度逐步拆分为独立服务。
5. **开发规模可控。** 初期可以通过手动派单和模拟支付完成核心流程，后续再补充消息通知、跨服务事务和运行监控等能力。

## 五、项目的初步边界与后续演进

### 1. 初步边界

项目初期面向单个社区，围绕报修到验收的核心流程开展开发。

**计划包含的功能：**

- 用户登录、角色权限管理，以及住户房屋信息管理。
- 报修工单创建、故障描述与图片提交、工单详情和进度查询。
- 物业审核报修、手动分配维修人员、协调上门时间。
- 维修人员接单、更新维修状态、填写维修记录及材料用量。
- 自费维修报价确认、费用明细展示和模拟支付。
- 住户验收、评价与返修申请，返修记录关联原工单。
- 基础材料库存管理，以及工单数量和处理时长统计。

**初期暂不包含的功能：**

- 多社区、多物业公司的复杂管理。
- 基于地图定位的实时轨迹和智能派单。
- 真实支付渠道对接、复杂财务核算和发票管理。
- 材料采购、供应商管理等完整供应链功能。
- 与智能门禁、传感器等硬件设备的联动。

公共设施维修和住户自费维修分别记录费用承担方式，自费维修需住户确认报价。同一维修人员的上门预约应避免时间冲突。工单状态变化需要符合规定流程，住户只能访问自己的报修记录。

### 2. 后续课程中的逐步演进

| 演进阶段 | 计划实现内容 |
|---|---|
| 数据库持久化 | 建立用户、房屋、工单、预约、维修记录、材料、结算和评价等数据表，完成基础增删改查与关联查询。 |
| 服务拆分 | 先按业务模块组织代码，再根据课程要求逐步拆分用户服务、工单服务、调度服务、材料服务和结算服务，明确接口及数据归属。 |
| 认证与授权 | 实现统一登录认证和角色权限控制，限制住户、维修人员及管理员的数据访问范围。 |
| 消息通信 | 通过消息队列处理派单通知、预约提醒和维修完成通知，并考虑消息重试与重复消费。 |
| 事务处理 | 先保证材料领用与库存扣减的本地事务一致性，再针对支付结果与工单状态同步等跨服务流程实践最终一致性和补偿机制。 |
| 系统监控 | 收集服务日志、接口耗时、错误率及消息积压情况，结合调用链定位跨服务问题。 |
| 部署与运行 | 完成服务容器化、配置管理和网关接入，逐步实现多个服务的协同部署。 |

该项目既有能够独立运行的基础业务闭环，也有清晰的模块边界和跨模块协作场景。前期可以用较小规模实现可用系统，后期再随着课程学习逐步引入微服务能力，每次演进都能对应实际业务需求，便于持续开发和验证。
