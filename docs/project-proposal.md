# 项目初步规划

> 本文沿用仓库 README 中的项目选题，仅记录业务规划。本阶段不实现业务模型、数据库或业务接口。

## 项目名称

**社区报修与上门维修服务平台**（完整选题名称：基于微服务架构的社区报修与上门维修服务平台）。

## 目标用户

| 用户角色 | 主要需求 |
|---|---|
| 社区住户 | 方便地提交报修，查看处理进度和负责维修的人员。 |
| 物业管理员 | 审核报修信息，按故障类别安排合适的维修人员。 |
| 维修人员 | 获取分配给自己的工单，了解故障位置和描述，确认是否接单。 |
| 平台管理员 | 维护账号、角色权限和维修类别等基础资料。 |

## 优先实现的业务场景

**住户提交报修，物业审核并派单，维修人员确认接单。**

例如，住户发现家中水管漏水，在平台填写故障描述、维修位置和期望上门时间。物业审核报修信息，选择具备水管维修技能的人员进行派单。维修人员查看工单并确认接单，住户能够查看当前处理状态。

计划流程：

1. 住户填写并提交报修，生成“待审核”工单。
2. 物业审核；信息不足时说明原因并驳回，住户可补充后重新提交。
3. 审核通过后，工单进入“待派单”，物业选择维修人员并派单。
4. 工单进入“待接单”；维修人员确认后进入“待预约”，无法接单时说明原因并退回“待派单”。
5. 住户查看工单状态和已分配的维修人员。

该场景优先解决报修信息分散、处理责任不明确和进度难查询的问题。正式预约、报价、材料库存、结算、评价和返修留待后续逐步扩展。

## 两个核心模型

以下模型及字段仅为初步规划，不代表已经创建实体类或数据库表。

| 核心模型 | 作用 | 初步属性 |
|---|---|---|
| 报修工单（RepairOrder） | 记录一次报修及审核、派单、接单进度，是核心业务对象。 | 工单编号、报修住户标识、报修类别、故障描述、维修位置、期望上门时间、工单状态、当前维修人员标识、审核说明、无法接单原因、创建时间、更新时间。 |
| 维修人员（Technician） | 表示可被物业安排维修工作的人员，为派单提供人员和技能信息。 | 维修人员编号、关联用户标识、姓名、联系电话、技能类别、是否可接单。 |

**模型关系：**一个维修人员可以负责多个报修工单；一个工单在同一时刻最多关联一名维修人员，未派单时可以不关联人员。

**初步约束：**派单时应检查维修人员是否可接单、技能是否匹配；维修人员只能确认分配给自己的工单；住户只能查看自己的报修。期望上门时间仅表示住户意向，不代表已经完成预约。账号、房屋及派单历史等其他模型在后续课程中再细化。
